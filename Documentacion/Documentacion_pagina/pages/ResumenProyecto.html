2. Problema del Hotel

El Hotel Santa Ana operaba sus procesos de forma completamente manual:

  • Las reservas se registraban en cuadernos físicos, propensos a pérdidas y errores de tachadura.
  • El estado de cada habitación (disponible, ocupada, en limpieza, mantenimiento) se controlaba con notas adhesivas y pizarras, sin trazabilidad.
  • Los datos de los huéspedes (nombre, documento, teléfono) se volvían a escribir en cada visita, aunque fueran clientes frecuentes.
  • El check-in y check-out dependían de la memoria del recepcionista para calcular horas extras y cobros.
  • No existía un historial de actividades: no se podía saber quién hizo qué ni cuándo.
  • La generación de reportes financieros requería sumar a mano decenas de páginas de cuaderno cada fin de mes.
  • El dueño no tenía forma de consultar el estado del hotel sin estar físicamente presente en la recepción.

Como resultado, el hotel sufría pérdidas por habitaciones que quedaban vacías por errores de agenda, clientes insatisfechos por demoras en el check-in, e imposibilidad de tomar decisiones informadas por falta de datos históricos confiables.

3. Solución Propuesta

Se diseñó e implementó HotelSoft, una plataforma integral compuesta por dos módulos:

Módulo de Escritorio (Java Swing)

  • Gestión de reservas: Creación, consulta (calendario y tabla), actualización y cancelación con búsqueda automática de clientes por documento.
  • Check-in y Check-out: Flujo completo con cambio automático de estado de habitación (Ocupada → Limpieza → Disponible) y registro en historial.
  • Gestión de habitaciones: CRUD completo con control de estados y precios.
  • Gestión de usuarios: CRUD con restricciones por rol (máximo 2 administradores, 3 recepcionistas).
  • Reportes y cierre de mes: Generación de reportes contables con totales de ingresos, reservas completadas y canceladas.
  • Historial de actividades: Registro automático de cada operación con tipo, descripción y fecha/hora.
  • Modo oscuro: Interfaz con tema claro/oscuro "Dark Blue" intercambiable en tiempo real.

Módulo Móvil (Flutter)

  • Dashboard administrativo: Visualización de ocupación, ingresos del día, reservas activas y próximos check-outs.
  • Métricas en tiempo real: Datos consumidos desde la API REST del servidor embebido en el escritorio.
  • Restricción de acceso: Solo administradores pueden iniciar sesión en la app móvil.

Comunicación Escritorio ↔ Móvil

  • Servidor REST embebido: El aplicativo de escritorio levanta un servidor HTTPS en el puerto 8443.
  • Autenticación por token: El móvil se autentica contra /auth/login y recibe un token UUID para las siguientes peticiones.
  • Endpoints: /habitaciones, /reservas, /stats, /reportes.

6. Base de Datos y Relaciones

Esquema SQL

-- Tabla usuarios: almacena las credenciales y roles del personal
CREATE TABLE usuarios (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    nombre   TEXT NOT NULL,
    usuario  TEXT NOT NULL UNIQUE,
    clave    TEXT NOT NULL,              -- hash PBKDF2 (desde v7)
    rol      TEXT NOT NULL CHECK(rol IN ('Administrador','Recepcionista')),
    telefono TEXT,
    correo   TEXT
);

-- Tabla habitaciones: catálogo de habitaciones con precio y estado
CREATE TABLE habitaciones (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    numero  TEXT NOT NULL UNIQUE,
    tipo    TEXT NOT NULL,
    precio  REAL NOT NULL,
    estado  TEXT NOT NULL CHECK(estado IN ('Disponible','Ocupada','Limpieza','Mantenimiento'))
);

-- Tabla clientes: información de huéspedes (normalizada en 3NF desde v6)
CREATE TABLE clientes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    nombre      TEXT NOT NULL,
    documento   TEXT UNIQUE NOT NULL,
    telefono    TEXT,
    correo      TEXT
);

-- Tabla reservas: vincula huésped, habitación y usuario que registró
CREATE TABLE reservas (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    id_habitacion   INTEGER NOT NULL REFERENCES habitaciones(id),
    id_usuario      INTEGER NOT NULL REFERENCES usuarios(id),
    id_cliente      INTEGER NOT NULL REFERENCES clientes(id),
    fecha_entrada   TEXT NOT NULL,
    hora_entrada    TEXT DEFAULT '12:00',
    fecha_salida    TEXT NOT NULL,
    hora_salida     TEXT DEFAULT '12:00',
    tipo_estadia    TEXT DEFAULT 'Noche',
    anticipo        REAL DEFAULT 0,
    estado          TEXT NOT NULL CHECK(estado IN ('Activa','Completada','Cancelada'))
);

-- Tabla historial: auditoría de todas las operaciones del sistema
CREATE TABLE historial (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    tipo        TEXT NOT NULL,
    titulo      TEXT NOT NULL,
    descripcion TEXT NOT NULL,
    fecha_hora  TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    id_usuario  INTEGER DEFAULT 0
);

-- Tabla cierres_mes: reportes financieros mensuales
CREATE TABLE cierres_mes (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    mes              TEXT NOT NULL UNIQUE,
    id_usuario       INTEGER NOT NULL REFERENCES usuarios(id),
    fecha_cierre     TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    total_ingresos   REAL NOT NULL DEFAULT 0,
    total_reservas   INTEGER NOT NULL DEFAULT 0,
    total_completadas INTEGER NOT NULL DEFAULT 0,
    total_canceladas INTEGER NOT NULL DEFAULT 0,
    notas            TEXT DEFAULT ''
);

Normalización

La base de datos está en Tercera Forma Normal (3NF):

  • 1NF: Todos los atributos son atómicos (no hay listas ni grupos repetitivos).
  • 2NF: No hay dependencias parciales; cada tabla tiene una clave primaria simple y todos los atributos dependen de ella.
  • 3NF: No hay dependencias transitivas. Los datos del cliente se movieron de reservas a la tabla clientes (migración v6), eliminando la redundancia de nombre, documento, teléfono y correo en cada reserva.

Las relaciones se mantienen mediante claves foráneas (id_cliente, id_usuario, id_habitacion) que referencian las tablas padre.
